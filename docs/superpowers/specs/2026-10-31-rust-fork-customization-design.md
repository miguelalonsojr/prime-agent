# Stage 1 Rust fork customization port: design

Historical approval reference: this document describes the 2026-10-31 port onto v0.10.2. The 2026-11-06 replay targets main at `73267c0f54242f420e3d52c70d42a785ecdca152`, keeps its existing installer and newer kernel behavior, and requires fresh verification. Historical results below are not results for the replay.

Status: approved by the owner on 2026-10-31. Stage 1 implementation is in progress. This scope amendment retains the approved contracts but removes model production changes already present in the pinned Rust release. The target is the immutable Rust v0.10.2 commit `ea9d9602ec0938d9e454e8963107cd85af1565c6` in `.worktrees/v0.10.2-fork-clm`. The source contract is one TypeScript customization commit `45b245c96d69ee7fb097c3b9cba7fdcdd993f33c`, relative to `v0.9.8`. Source code references below refer to that customization commit. Rust references refer to the pinned target release. The test-intent table and producer/consumer traces carry the evidence needed to review the scope.

## Intent and scope

Port the source commit's missing user-visible and safety contracts into Rust-native code while preserving Rust v0.10.2's session, worker, terminal, model registry, and Python-kernel architecture. A completed Stage 1 supports a local checkout installer, interactive `/term` with final shell directory applied to the agent kernel, kernel-CWD status and next-turn notice, optional capability-gated daemon transport, manually authenticated RLM child selection, peer grant generation fencing, ordinary worker adoption identity fencing, and the bundled routing/rehydration regressions. Existing Rust implementation can satisfy a source contract when its behavior is equivalent.

Stage 1 does not restore the TypeScript application, implement CLM, migrate user data, or claim safe TS session/CLM resume. Stage 2 is a separate native Rust CLM design and validated one-way import of old CLM sessions into Rust-owned copies. The existing Python kernel runtime remains part of the Rust product. Stage 1 does not add a new library, transport, state store, model catalog, or sparse-delta reconstructor without a demonstrated need.

Success requires observable behavior rather than a line-for-line TypeScript port. Failure includes a launcher that works only from the checkout directory, a shell `cd` that changes only the UI process, a CWD command sent to an old daemon, an unauthorized model admitted because it is the parent's selector, a pending peer ticket accepted after its supervisor claim is lost, or an ordinary stale worker descriptor adopted through either race path. No source regression may be dropped without evidence that the Rust transport makes it inapplicable.

## Approach and decisions

The user chose a Rust feature port in the new worktree, with the customization before CLM. A direct cherry-pick cannot apply: the customization changes removed TypeScript application paths. Reintroducing the TypeScript application would conflict with the Rust target and is not the selected approach. Reimplementing every TypeScript module verbatim would duplicate Rust kernel, daemon, and TUI ownership and is not proposed. The chosen design ports each behavior into the existing Rust owner and reuses equivalent Rust paths. The independent safety trace establishes that the TypeScript compact-delta guard has no Rust destination; no sparse-index patch is planned.

Proposed builder decisions, not new user requirements: (1) the local launcher runs the Rust checkout's release binary and binds `PI_PACKAGE_DIR` to the absolute checkout root, rather than invoking removed `prime-agent.sh --dist`; (2) keep the existing Python runtime and use its kernel manager for CWD probes; (3) use the existing TUI terminal-handoff and reader-stop cycle for `/term`; (4) preserve the source JSON field/capability strings for the added optional daemon surface, but choose a new Rust schema ID and revision from the target's actual schema ledger; (5) preserve the source `term_cwd_changed` hidden-message custom type and `{cwd}` details for durable notices. These are reviewable design calls. They do not assert live TS/Rust daemon or session-file interoperability.

## Ownership and execution paths

### Local checkout installer

Add a local checkout command (`scripts/install-local.sh [--force]`) separate from `install-rust.sh`, which installs downloaded or local release archives. The local command builds the checkout rather than downloading a prebuilt application. Cargo may need to fetch dependencies from the committed lockfile; offline installation is not a new promise. The script resolves its own checkout root to an absolute path, requires `HOME`, validates the sole optional flag, and refuses an existing command unless `--force`. It always refuses a destination directory. A dangling destination symlink counts as an existing command. It builds the Rust `pa-cli` release binary in the checkout before touching the old launcher. The builder must check the project's actual Cargo build output and packaging checks; the design does not assume the currently absent `target/release/prime-agent` already exists.

The published launcher invokes the built checkout binary by an absolute shell-quoted path, passes arguments with `"$@"`, and keeps the caller's working directory. It binds the executable's asset lookup to the absolute checkout (`PI_PACKAGE_DIR`) so a command run from any directory finds that checkout's `prime-agent-runtime`, built-in `skills`, and `docs`. `pa-core/src/kernel/bootstrap/venv/runtime_source.rs:10-57` checks `PI_PACKAGE_DIR/prime-agent-runtime`, validates `pyproject.toml` and `src/rlm`, then falls back to a compile-time checkout root; `pa-core/src/packages/mod.rs:48,97-125` resolves checkout assets; `pa-cli/src/config.rs:49-77` falls back to the compiled version if no exe-adjacent `package.json` exists. The runtime must not resolve from whichever directory happens to call the launcher. The binary's own `current_exe` path remains the checkout build for daemon spawning (`pa-cli/src/interactive_mode/daemon.rs:58-88`). Preserve the source shell's path with apostrophes and argument fidelity; do not replace an old launcher if build or publication preparation fails. Create a temporary file in `~/.local/bin`, make it executable, and rename over a file/symlink only after successful build. Clean temporary state on failure/signals; show a PATH hint when `~/.local/bin` is absent. Source `scripts/install-local.sh` is a short build-before-rename implementation, but its `npm run build` and `prime-agent.sh --dist` commands are not Rust payloads. Existing `install-rust.sh` release/update behavior stays unchanged.

Installer checks use isolated HOME and fake builder/binary fixtures for collision, `--force`, dangling symlink, unknown args, directory refusal, failed build preserving the old command, apostrophe path, quoted argv, caller CWD, PATH hint and no real-home write. A real build and command invocation from outside the checkout must also prove Python runtime and skill resolution. The verified checkout-bound launcher intentionally follows later rebuilds at the same binary path; checkout removal makes it unusable, matching source checkout binding. It does not copy or migrate session files.

### Shell, kernel and client status

`pa-types/src/slash_commands.rs` registers local no-argument `/term`. `pa-tui/src/session_ui/commands.rs` rejects arguments, Windows, and interruptible work before allocating a shell. After those refusals, it reads `ClientSettings::shell_path() -> Option<PathBuf>` once for this command, then chooses that configured shell, `var_os("SHELL")`, or `/bin/sh`. The default getter returns `None`; `CliClientSettings` overrides it with `self.manager().settings().shell_path.as_deref().map(PathBuf::from)`. The existing `SessionUi` client-settings handle carries this setting. The adapter reads current merged settings for its fixed resolved-run `cwd` and `agent_dir`, not the kernel's later CWD. No settings read occurs during paint, and a selected shell that fails to spawn reports an error without trying the next fallback. It starts from effective kernel CWD if that path remains a directory, otherwise from session CWD. It echoes the local command and reports errors or warnings without changing the selected session CWD on failure. Linux and macOS must observe the shell's final directory. Process-CWD polling alone loses rapid `cd; exit`; preserve exit-time CWD hooks for bash, zsh, fish, and supported POSIX shells while retaining normal shell initialization, as in source `shell-session.ts::createShellLaunch`. Preserve the shell exit code even when the hook writes the final path. Validate that the reported final directory still exists and is a directory before propagation. Windows refuses `/term`; unsupported observation on any other platform warns rather than changing the agent state.

The terminal owner is `pa-tui/src/interactive/run.rs`. It already stops its input reader, shields SIGINT, suspends the renderer, runs an external editor, restores raw mode/alternate screen/enhanced keys/mouse tracking, resumes the reader and repaints (`run.rs:1044-1102`, `interactive/render.rs:319-364`). `/term` uses that ownership pattern. The shell runner owns the child, polling/hook files, and cleanup. An error, cancellation or shell failure must restore the TUI and input reader in a finalization path. A shell's nonzero exit is not by itself a CWD propagation failure. An unsupported shell or missing shell reports an error and restores the terminal. `/term` does not use the daemon's persistent bash session feature or alter the process's global CWD.

`pa-core` owns one effective per-session kernel CWD, distinct from immutable session creation CWD. Add the smallest session-facing `set_kernel_cwd`/read seam needed by the daemon worker and in-process host; do not create a second authoritative CWD in the TUI. Validate an absolute directory before mutation. Before kernel boot, update the provisioner's requested startup directory; after boot, execute an internal `os.chdir` in the current kernel, read back its effective directory, update the next-boot setting, then publish the changed event. A failed live change must leave the previous CWD and notice unchanged. Source `agent-session.ts:14190-14218` enqueues a hidden `term_cwd_changed` next-turn custom message with `details: { cwd }` after successful application, including an unchanged valid path; retain that behavior. The message text tells the agent its kernel now runs in the selected directory. Use the existing next-turn custom-row queue (`pa-core/src/session_engine/{mod,admission}.rs`) and normal session artifacts/recovery; do not add a new durable snapshot schema solely for the notice.

Observe programmatic `os.chdir` after every settled public `python_repl` cell, including a returned error status. The source hooks at `ipython.ts:739-760` and `agent-session.ts:8612-8628`; Rust's public tool path is `pa-core/src/tools/ipython.rs:362-485`, via `session_engine/runtime_wiring.rs:342-403` to `kernel/manager/mod.rs:583-612`. Place the best-effort, bounded internal `os.getcwd()` read after the matching external kernel cell has actually completed, not at arbitrary TUI paint or in the generic kernel manager's internal probe path. An aborted public tool result can precede the matching kernel `Done`; it is not permission to start another execution. Use the existing completion and generation ownership signals to avoid overlapping probes or publishing a stale provisioner's directory. This observation must not prolong the public abort response. It must not replace settled output, cause recursive observations, or schedule snapshots for probes. The public Rust execution entrypoint schedules snapshots after successful execution; dedicated internal state requests bypass that scheduler. Use the existing internal request path for CWD probes and preserve snapshot behavior. Publish `kernel_cwd_changed` only when the observed path differs. Make preboot/rebuild kernel construction use the stored effective CWD without racing the old provisioner's final snapshot flush. A session resume's effective CWD must be reconciled with actual restored kernel state before claiming it in the UI; existing persisted notice/queue and kernel restore ordering determine that result.

The daemon connection snapshot carries optional `kernelCwd` separately from the session `cwd`; TUI display falls back to session CWD when absent, including successive legacy snapshots. The event carries `{ type: "kernel_cwd_changed", cwd: string }`. On confirmed changed effective CWD, refresh autocomplete and footer. The existing `interactive/run.rs` refresh calls `Editor::set_autocomplete_file_base(&mut self, base: PathBuf)`, not a path from a successful request alone. The editor cancels its menu, pending completion, and active search through `cancel_autocomplete`, then forwards to an installed provider; it does not install one when absent. `AutocompleteProvider::set_file_completion_base(&mut self, base: PathBuf)` defaults to no-op. `CombinedAutocompleteProvider` keeps commands, skill commands, hidden filters, and argument completions while changing its path base and replacing its file index with a fresh `FileIndex` plus background start only when the base differs. The old index and queued search results cannot supply completions for the new base. This adds no index/search internal or test-support change, settings read, network fetch, or dependency. Footer renders home-abbreviated path and the current Git branch, except no branch outside a repository. It fits narrow terminals and gives active `/speed` text precedence without making the speed-off footer empty. Git discovery and filesystem work must not block the paint path. Cache or offload that work and update the footer when the result changes; preserve the Rust TUI's latency rule. The source `footer.test.ts` and target `pa-tui/tests/speed_footer_headless.rs` define the tests, not a new cross-crate Git service.

### Optional daemon protocol and compatibility

`pa-types` owns JSON wire vocabulary, event, command enum, capability metadata and session-plane/mutation classification. The optional snapshot field belongs to the existing `AgentConnectionState` in `pa-daemon/src/types.rs`. Propose the source field names `activeSessionId`, `dir`, `kernelCwd`, `cwd`, command `set_kernel_cwd`, event `kernel_cwd_changed`, and capability `kernel_cwd_propagation`. Existing Rust protocol is version 7, schema revision 30 with a Rust-specific schema ID (`pa-types/src/daemon/mod.rs:12-17`). Treat this as a backward-compatible optional feature behind a negotiated capability, not a required startup command or an incompatible protocol bump. Add a new Rust schema revision and ID per the Rust ledger. The client sends `set_kernel_cwd` only when protocol 7, new minimum schema revision, and advertised server capability all pass. If any gate fails, `/term` may open but CWD propagation reports a local warning; legacy `get_connection_state` and normal session operations remain usable. The client must not write an unsupported command to the socket. Old clients ignore the optional snapshot field and unknown event; new clients use session `cwd` when `kernelCwd` is absent. The worker mutates the addressed session only and emits the event after application; supervisor routing and direct worker link must preserve the same ID, payload and response.

The source `daemon-launch.ts:76-80` reuses a daemon only when app version and protocol match and either the schema ID matches or the daemon advertises a strictly newer schema revision. Rust `pa-cli/src/daemon_discovery/mod.rs:406-415` currently requires exact ID. Apply the source rule to daemon startup/discovery reuse without turning a different same/older/missing revision into a compatible daemon. Capability checks still gate optional commands even against a newer schema. Reuse does not imply that unrelated newer fields or commands are understood. Test both new client/old daemon and old client/new daemon, a newer-ID/newer-revision reuse, and different equal/older/missing revisions as stale. Test a busy stale daemon without stopping it. A matching numeric TS revision does not prove TS/Rust live daemon interoperability; the supported combinations and byte-level compatibility require an explicit verification matrix before any such claim.

Task 3 verification needs a successful-observation receipt to prove that an unchanged public cell emits no worker CWD frame. The worker must not infer observation completion from tool return or an empty event receiver: the core callback runs after the matching kernel `Done` and schedules its read separately. Declare a default-off `test-support` feature in `crates/pa-core/Cargo.toml` and add a dev-dependency entry for the existing local `pa-core` crate in `crates/pa-daemon/Cargo.toml` to enable `test-support` only in daemon tests. Under `cfg(any(test, feature = "test-support"))`, `pa-core/src/kernel/provisioner.rs` may expose a small per-provisioner receipt/API for a successful current-manager CWD observation. Emit the receipt after actual readback, change suppression and any synchronous changed callback; emit nothing for skipped, stale or failed probes. The receipt remains independent of the changed guard so bypassing unchanged suppression fails a strict worker frame-count test. The daemon test accesses the provisioner through existing `AgentSessionEngine.kernel_cwd_probe`. No ordinary-build hook, new package, lockfile change, `SessionEngine` trait method, daemon forwarding or wire API, global witness, tool-completion await, or kernel lifecycle redesign is authorized by this verification seam. This amendment specifies a test boundary; it does not claim implementation or test results.

### RLM model discovery and child restoration

The customization changes `agent-session.ts::_authenticatedRlmModels` from `getExecutableModels()` to `refreshAvailableModels()`. The TypeScript parent already called `refreshAvailableModels()` inside `getExecutableModels()` before intersecting Codex models with `/codex/models` (`model-registry.ts:1234-1286`). The new behavior removes account-list filtering; it does not introduce query-time refresh. At pinned Rust `ea9d9602`, `pa-core/src/models/registry.rs:206-249,456-515,544-576` composes locally defined and compiled auth-configured models without an account-model intersection. `session_engine/rlm_host.rs:518-554` searches that registry; `pa-daemon/src/rlm_child_model.rs:28-42,70-116` resolves inherited, exact, and unique short selectors; `rlm_children/host.rs:114-121` applies allowed-model and supported-thinking gates. The native Codex provider resolves request credentials and sends the selected model at request time (`pa-ai/src/providers/openai_codex_responses/request.rs:36-94`, `mod.rs:619-695`). No new model registry or selection production change is required for this customization delta.

Retain the existing native auth/status, private entitlement, allowed-model, thinking, and request-time authentication behavior. Do not add a pre-create policy for expired or empty credentials: discovery status does not prove every credential is usable, and the native request owner still validates it. Query-time reload after bridge construction, stricter upfront authentication, and transfer of an active full `Model` when its definition has disappeared from local registries are inherited gaps outside this port. Do not change the public `RlmHostBridge` registry signature, add `Arc<Mutex<ModelRegistry>>`, implement `rlm_auth_status` or a new preflight API, rewrite the resolver, or add child-host offloading for unapproved preflight work. The unintegrated Task 5 production draft is retired; its review findings remain archived as findings against that draft, not accepted production behavior.

Test the missing end-to-end combinations against unchanged native production. Use a locally defined, noncompiled Codex-compatible model with valid synthetic auth. Prove actual registered discovery, child creation/completion and native provider POST, with no `/codex/models` request. Separately reopen and passively wake a saved child without parent model/effort overrides; its next actual provider POST must retain the explicit selector and `low` effort. Reuse existing selector/auth/header and saved-state unit tests instead of duplicating them. Existing `get_api_key_and_headers` suffices if a direct request test needs auth; do not invent a new API. Source-path evidence is not an executed test result. A first passing native test demonstrates reuse; bounded mutations of the actual discovery, delivery and recovery owners must make the retained assertions fail, with exact source restoration after each completed command. No real credentials or paid provider calls belong in CI.

### Peer grants and worker adoption

A peer grant is minted by the supervisor and stored in the worker; peer authentication removes it before checking credentials. Rust `PeerGrantStore::register` checks issuer generation at registration, but `authenticate` checks no live supervisor claim (`pa-daemon/src/peer.rs:129-197`). The worker must track a current live generation-bearing supervisor claim or equivalent coordinated invalidation, not only its current connection count (`worker/connection.rs:613-638`). An old connection's teardown must not erase a newer claim. Before admitting a burned grant, compare its issuer with the currently live supervisor generation. If the claim is absent or different, refuse, close the peer socket, and leave the grant consumed. Legitimate same-generation reconnects are not rejected merely because the connection changed. This change fences pending grants only; it does not require evicting already-authenticated peers after supervisor loss. Preserve existing token, expiry, purpose, worker-incarnation and session-scope checks. Test loss and replacement during the grant TTL with both ticket purposes where practical, plus valid same-generation admission and failed replay.

The supervisor's persisted worker descriptor has PID and process-start identity. Its existing boot census (`pa-daemon/src/boot_reap.rs`) runs before both adoption paths and otherwise reaps a same-socket worker with a positively mismatched descriptor identity. Protect that worker narrowly before ordinary adoption can refuse it. Retain the readable/version-2/same-normalized-socket/nonzero PID gates, use checked PID conversion, and retain the unconditional `stop_requested_at` exclusion. Preserve the existing protection for matching or unavailable identity observations. Add protection for a positive mismatch only in `Starting`, `Ready`, `Recovering`, or a `Failed` descriptor carrying the exact internal ordinary-identity-refusal `last_error` reason `Recorded worker process identity differs from the observed process`, shared with the failure writer. `Stopping` and unrelated `Failed` descriptors do not gain protection. Do not change descriptor schema, signal/census behavior, monitor ownership, fresh replacement, or tombstone finalization. A real restart and a second restart after the identity-refusal `Failed` write must leave the original worker responsive without replacement, stop or retirement. Keep descriptor-less orphan and different-socket boot-reap cases, along with stop/give-up coverage. This boot exclusion does not authorize admission. Both the descriptor-scan path (`supervisor/adoption.rs:200-385`) and registration-first path (`:396-711`) must compare the recorded identity with a positive observation for that recorded process before adopting or overwriting the recorded value. Use the existing per-worker adoption guard to keep the check and admission in one race boundary. An observed mismatch refuses admission, marks the descriptor failed through its existing failure path, and does not attach, stop, kill, or tell the worker to self-retire. An unavailable observation is not a mismatch; it must preserve the recorded identity and allow normal authenticated adoption. Keep tombstone stop-finalization, intentional fresh-worker launch/replacement, identity-pending reconciliation and existing monitor ownership unchanged. A new refusal and its wrapped context must not contain `Unknown session worker`, because `registration.rs` matches that substring to trigger definitive self-retirement. Do not send stop commands to an unverified socket or signal a reused PID. Tests must interleave registration before scan and scan before registration with a live worker and stale descriptor behind a barrier-controlled observation while the other route waits for the adoption guard. Sequential invocation of both routes is not a concurrency proof. Check both refuse and leave the worker alive; transient observation unavailability still adopts and retains the identity. Mutation of the boot exception must fail the real restart case; separate mutations of each admission guard must fail its own ordering case. Negative selection tests cover tombstones, `Stopping`, unrelated `Failed`, foreign/malformed descriptors and zero/overflow PID.

### Full-message stream and regression-only contracts

Do not add a sparse-index patch. The independent trace follows `agent_engine/turn/run_once.rs:181-196` full `AssistantSnapshot::Loop` -> `worker/turn.rs:717-789` -> `streaming.rs:69-101,135-168` full partial `message_update` -> direct/routed `client_event_from_value` -> `pa-tui/src/snapshot/decoder.rs:218-249` consuming `event.message`. No consumer inserts a block by `contentIndex`; `session_engine/session_events.rs:14-115` emits index metadata and uses `.get()` for thinking text, not indexed writes. The source `compact-session-stream.ts` sparse-write guard cannot fail on this Rust route. Document its four sparse rejection and replacement/append intents as inapplicable to this route, and keep existing full-snapshot streaming tests. If compact-delta reconstruction is later introduced, port those six cases at its insertion boundary.

The source also adds regression-only tests without related production hunks. Keep direct and supervisor fallback routing of model, thinking, scoped models, and each timeout intact; add only missing receiver-observed payload and timeout combinations. Do not replay a request that was sent but timed out. The existing `command_breadth.rs` covers the known native command list and parser fixtures; extend it for the new kernel-CWD command and the narrow missing metadata/fixture invariant without adding a unified metadata architecture or repeating its existing breadth. Recover a persisted RLM child and prove its actual faux-provider request uses its saved model and low thinking in the test-only model task. Do not delete these intents as “already upstream” based on a test name.

## Baseline record and scope boundary

The pristine baseline ran at `ea9d9602ec0938d9e454e8963107cd85af1565c6` before any tracked changes. Rust format/check/Clippy, the dependency audit, Linux release packaging, and Windows GNU check/Clippy exited successfully. The Python runtime suite passed 748 tests in the corrected isolated interpreter setup. The script suites passed 141 tests. Existing vendor and runtime warnings remain recorded.

The first eight-shard Rust run executed all 235 selected units and reported 5,846 passed, 19 failed, and 20 ignored tests. It was not CI-equivalent: the runner leaked step-local interpreter and TypeScript-reference variables across jobs and used an overlong temporary directory. The goal failure has an environment cause.
