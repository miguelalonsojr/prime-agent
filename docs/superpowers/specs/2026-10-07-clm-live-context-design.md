# CLM live context for TypeScript Prime Agent

## Purpose and scope

Prime Agent can opt into Context Language Model (CLM) behavior. The model edits a readable working conversation in a session-local file. Accepted edits change subsequent provider requests. Original session messages remain available as an audit. The feature aims to maintain task quality, reduce cost per successful long task, and make the actual model context inspectable. None of those outcomes follows from a shorter prompt alone; evaluations must measure them.

This design targets the TypeScript fork at `45b245c96d69ee7fb097c3b9cba7fdcdd993f33c`, one commit above `v0.9.8`. The separate experimental Rust fork at `0649d9e1deaf7471874d78ee04ae772292e98217` informs failure cases and tests, but its Rust changes cannot be replayed onto this branch. The Meta reference is CC BY-NC 4.0. Implementation must be independently written; do not copy its code into Prime Agent without license clearance. The Rust fork's MIT declaration does not establish the provenance of Meta-derived code.

V1 does not add model training, suffix-cache reuse, a context-sharing protocol between agents, or a human editing interface. A human can inspect the accepted context and full audit. A user who changes the file directly outside the model's awaited tool action uses an unsupported path; the runtime must not silently attribute that change to the model.

## Existing boundaries

`SessionManager.buildSessionContext()` reconstructs the active branch and compaction state from session entries (`packages/coding-agent/src/core/session-manager.ts`). `AgentSession` holds the live message array and rebuilds it after compaction or navigation. Each provider request passes through the context transform in `packages/agent/src/agent-loop.ts` and the coding-agent SDK. Original entry bodies must not be edited to implement CLM. Session JSONL may already be rewritten for migration or recovery, so “audit preserved” means CLM never replaces original message content, not that its physical file is immutable.

The system prompt and tool definitions are separate from live history. The skill catalog is included in the system prompt. Full `SKILL.md` text read through a tool enters ordinary message history. CLM may remove that old tool output when it is no longer useful. Static project context such as `AGENTS.md` must not become the editable conversation file.

The three considered approaches were an editable provider projection with versioned revisions, an editable compaction summary, and rewriting session JSONL. The projection is selected. A summary does not let the model reshape other history, and rewriting original entries discards audit provenance and risks tool-call structure.

## Mode and session transitions

The existing global/project settings system gains a `clm.enabled` default for new sessions. It does not flip an active session when a settings file changes. An idle session accepts `/clm on` and `/clm off`; the explicit session choice persists across restart regardless of later default changes. An active request, queued retry/continuation, or uncertain tool writer rejects the toggle with an actionable busy error. The effective mode is reconstructed from durable mode entries on the selected session branch, not from the current settings file or disposable working file. New mode entries record whether CLM was enabled by the configured default, inherited child mode, or an explicit session choice; an explicit off transition records the session choice. The source is branch-local. Older entries without this field report `unknown` rather than inferring a past choice from current settings. A no-op toggle does not rewrite the source. Status reports the current configured default separately from the recorded source and lists a bounded set of recent accepted revisions from the selected branch.

`/clm on` initializes an enable epoch from the session's current model-visible messages, including any prior compaction projection. A flushed `clm_on` session entry contains that initial accepted snapshot and an audit-entry watermark. The runtime then publishes a model-writable `clm/context.txt` under that session's artifact directory. The model receives the absolute path and edits it with existing tools in a single awaited action. A later `/clm on` begins a new epoch from the then-current normal context; it does not resurrect history removed in an earlier epoch.

`/clm off` flushes one self-contained `clm_off_boundary` session entry that contains the last accepted semantic messages, required attachment payloads, the audit-entry watermark, and the off transition. That entry is the commit point: before it is durable, recovery remains CLM-on; after it is durable, normal reconstruction starts from its snapshot and subsequent messages without reading CLM artifacts. The runtime stops reading the file only after this flush succeeds. The full audit stays inspectable. Normal compaction, navigation, and forks from the frozen boundary or its descendants then work without a reference to the former session's artifact directory. Explicit navigation to a pre-CLM audit node can restore older audit content only after a warning/confirmation. Navigating to an earlier CLM-epoch node must reconstruct that node's accepted revision from its branch entries and enforce CLM guards again, rather than silently reconstructing audit text.

New `rlm.spawn` children inherit the parent's effective CLM mode at admission. Each child has its own file, revisions, audit, and protected current task. Children already running do not change when the parent toggles. CLM-on spawn during an active ipython tool action requires a runtime-owned cell execution ID in the Python host-request envelope, bound by the kernel to that exact live tool action. Model-supplied kwargs and generic host payloads cannot assert ownership. A detached earlier cell, a direct caller without verified origin, or an older runtime without origin metadata cannot borrow another action's writer marker; active-writer admission fails closed for them. The envelope field is optional for normal-mode compatibility and changes neither the daemon protocol nor accepted JSONL. Historical `/fork` and CLM-parent branch navigation are distinct from subagent spawning and remain guarded while CLM is on.

## Model context and edit semantics

For every provider request in CLM mode, the session engine supplies the accepted context revision rather than the canonical audit reconstruction. System/developer instructions, project instructions, tool schemas, and the skill catalog stay outside the editable file. Each delivered user request has a session-action identity and stays protected until that owned action settles, including its retry chain, tool calls, continuations, and serialized event persistence. `turn_end`, `agent_end`, delivery, or an idle agent flag alone does not release protection. A steering or follow-up request has its own action identity; once delivered it stays protected until that action settles. Completed tool groups from an ongoing action can be edited while its user request remains protected. A cancelled or failed request becomes editable only after action cancellation and the writer/persistence fences settle; a later retry is a new protected action. Prime Agent sessions can contain many tasks, so the first request is not pinned forever. Loaded skill text remains editable history.

The file represents completed messages and tool groups, including completed groups from an ongoing protected request, in a readable form with stable identifiers. The renderer escapes content that looks like a control header. A parser validates roles, identifiers, image references, and size before accepting an edit. Editable text cannot create a system/developer message or execute a historical tool call. Unknown attachment identifiers and malformed protected references fail validation. Unchanged structured calls, results, and attachments retain their native provider representation. Edited historical tool groups become inert user/assistant text as needed; no orphan call/result pair reaches the provider. The current in-flight call and its result are appended after the historical edit is synchronized. An edited file never changes the current protected user request.

CLM tool actions run sequentially. A session-owned CLM writer lane fences the existing agent-event queue and session-input actions before file import, revision commits, completion receipts, child-message delivery, and provider-request snapshots; an event-listener return alone is not a persistence barrier. Before opening a tool action, the engine checks the published file hash and refreshes the mirror with newly completed historical messages. It then imports a change only after the underlying tool execution and its writer have actually stopped. `raceWithAbort` can end an agent-loop wrapper before `tool.execute` finishes, so cancellation must not release file ownership or accept that action's late edit. If writer quiescence cannot be established, the session durably marks the enable epoch conflicted, refuses CLM requests/toggles until the writer is stopped and the mirror repaired from the accepted revision, and preserves that revision rather than treating an idle wrapper as settled. The conflict marker is an existence-only, fsynced operational file beside the canonical persistent session JSONL, not part of the disposable context mirror or an accepted revision. Arm it and fsync its directory before admitting a CLM tool action. Clear it and fsync the directory only after the known physical writer has settled and the accepted mirror is repaired. Cancellation leaves the marker until explicit repair. On restart without the original writer receipt, an empty queue, unchanged file hash, or elapsed time is not proof of settlement; keep model work and mode changes blocked while leaving audit attachment available. This marker cannot certify arbitrary bash, Python, extension, or detached writers. A changed file seen before an action is also a conflict. Records identify the action during which an edit was observed, not a verified author: an external write during the action is indistinguishable with shared filesystem permissions. Detached or concurrent writers are unsupported; an atomic save alone does not provide multi-writer isolation. The existing tools are not a filesystem sandbox, and an agent with user-level filesystem permissions can still access other paths.

When no edit occurs, new messages append normally to the accepted context. An invalid edit leaves the last accepted revision intact and returns a clear tool observation. The working file is repaired or quarantined without erasing the rejected content. File import and budget validation occur before any next provider request. The budget estimate includes fixed instructions, tool definitions, attachments, and output reserve. It is not an exact provider tokenizer or a guarantee of lower billing. Near-budget feedback prompts the model to shorten stale context. A request projected over budget fails before dispatch; the user can restore an earlier accepted revision or turn CLM off and use normal-mode compaction on the frozen accepted boundary. Restoration is an explicit new revision with the current audit watermark, not an in-place change to old entries. The runtime never silently substitutes the full audit.

## Durable store and recovery

The session JSONL branch owns numbered `clm_revision` entries. Each entry holds a complete accepted semantic snapshot, base revision, content checksum, observed tool-action ID, and an audit-entry watermark. Original message entries remain unchanged. The model-facing projection uses the latest accepted entry on the selected branch plus only later audit messages not covered by that watermark. It does not use global file-last order. The working `context.txt` is a materialized editable mirror, not a recovery authority. A revision must be flushed before it is reported as accepted or used in a provider request. This can cost disk space proportional to the number and size of edits, so revisions and working files have bounded sizes. Checksums detect accidental corruption; they do not authenticate a writer with the same filesystem permissions.

The session writer lane orders audit message entries and CLM revisions. Each accepted snapshot's watermark and stable tool-result receipt identify which audit entries it includes; recovery consumes a result at most once and never adds older messages merely because a CLM snapshot is missing. A crash before a complete durable `clm_on`, `clm_revision`, or `clm_off_boundary` entry leaves the last confirmed branch state authoritative; a torn or uncertain append pauses provider requests until the session log is repaired and checked. SessionManager can defer pre-assistant writes and rewrite damaged JSONL, so CLM commits require an explicit durable flush and validation rather than assuming ordinary append timing. On restart, a missing or corrupt accepted revision for a branch marked CLM-on is an error, not permission to seed from the full audit. External tool effects are not part of that transaction; a tool can have run even when its result delivery is uncertain.

Accepted entries record observed edit provenance and support later inspection or explicit restoration. V1 does not promise secure deletion: the audit, revision entries, external files, and providers may still retain removed text. A snapshot shown to the user is the accepted head, not pending filesystem bytes. Older Prime Agent binaries that do not understand CLM entries must not resume a CLM session: the current version-3 loader can ignore unknown custom entries and otherwise reconstruct the original audit. The release and recovery UX must warn against such downgrades; the new loader must detect and handle CLM markers on every resume path.

## Unsupported CLM operations and helper calls

While CLM is on, manual/automatic compaction, overflow compact-and-retry, historical branch navigation, `/fork`, and side questions return CLM-specific errors. Default-mode sessions keep their existing behavior. A helper model call, including refinement, must use a pinned accepted CLM snapshot or fail before it calls a provider. It cannot use forgotten audit messages as an undocumented fallback. Agent-to-agent messages and durable goal observations append through the same session writer lane. CLM must not disable normal `rlm.spawn` subagents.

A failed assistant turn removes only its known failed provider entry from the accepted context. It does not replay external tools or remove arbitrary edited notes. On `/clm off`, the guarded operations become available against the frozen accepted boundary. Corrupt CLM data must not prevent attachment or access to the original audit and repair information, even when provider requests cannot proceed.

## Interface and daemon compatibility

`/clm on|off` implements the idle toggle. `/clm status` reports effective mode, source setting or session override, file path, accepted revision, recent revision IDs, estimated context occupancy, and any validation/recovery error. `/clm restore <epoch:revision>` is an explicit recovery operation available only while CLM is on. The target must be a valid accepted revision in the current epoch on the selected branch, not a revision from an abandoned branch. Restore waits for settled session actions, writer quiescence, and persistence fences, then appends a new revision of the selected snapshot with the current audit watermark; it never rewrites the audit or re-enables CLM after `/clm off`. It can clear a file conflict only after the late writer is confirmed stopped and the mirror has been republished from the selected revision; corruption of the session log itself still requires explicit repair. A read-only context view displays accepted model messages with revision and explicitly labels them as distinct from full audit entries. A single session-owned read captures the selected branch, epoch, revision, and copied messages under the same writer/action fence. The revision labels the accepted edit baseline; uncovered later audit messages can extend the model view without a new edit revision. This read does not import or accept pending `context.txt` bytes, repair the working file, or dispatch a provider request. If there is no valid accepted boundary or recovery is uncertain, the optional view fails locally and audit attachment remains available. Estimated occupancy may be absent or stale; it is never presented as billed usage. Task 9 exposes the copied result through an optional negotiated daemon command. Existing `/context` cost and token reporting remains available; Task 10 owns its presentation and keeps that report usable if the optional CLM status lookup fails. Task 11 supplies observed usage data without formatting terminal text.

New daemon commands, events, and response fields for mode and snapshots are optional negotiated capabilities. Their wire changes update `DAEMON_SCHEMA_REVISION`, command/event compatibility maps, and new-client/old-daemon and old-client/new-daemon tests. Bump `DAEMON_PROTOCOL_VERSION` if any change is incompatible or startup requires behavior an old daemon lacks. An old daemon must reject `/clm` with a local message while allowing normal session attachment. A snapshot failure must degrade the optional panel locally; it cannot fail startup or attach.

## Verification and evaluation

Deterministic tests use a faux provider and assert the actual next request, not a parser's private return value. They cover unedited versus edited native tool structure, role and image validation, request-action protection across tool turns, steering, retries and abort, skill-history editability, over-budget rejection, sequential tool ordering, child inheritance, toggle persistence, and disabled-mode behavior. Fault injection covers a cancelled writer completing after the abort wrapper (with deferred signals, no sleeps), stale pre-action file drift, each durable on/revision/off boundary, torn JSONL, audit-watermark replay, self-contained branch/fork after off, and old/new daemon compatibility. Tests cover valid, stale-branch, and off-mode `/clm restore` requests and prove failure when a covered production behavior is broken. They also race an accepted-view read with restore, verify pending file edits do not enter the view, show legacy mode-source and usage fields as `unknown`, and reopen after completed receipt writes without treating an unfinished request as billed usage. Concurrency/ordering suites run across multiple shuffle seeds. Each modified test file runs directly under the project's test policy. No CI test uses paid provider APIs or real credentials. The project prohibits generic `npm test`; a test run requires a specific approved test target.

At dispatch, each actual provider request pins its selected branch, effective mode, and accepted epoch/revision when present. A versioned, additive completion receipt in the session JSONL associates the observed provider-only usage with that pin; main and helper provider calls follow the same rule. A failed-provider cleanup revision creates no billed receipt. Receipts that reach disk survive normal reopen and branch navigation. An unfinished call or an observed completion lost before the ordinary session write reaches disk has unknown attribution, not zero usage; V1 adds no extra crash-safe flush for telemetry. Unknown or older receipt versions never become model-context authority, and existing audit usage totals remain unchanged. Reports distinguish estimated occupancy from measured input, output, cache read/write, total billed cost, edit count, edit size, rejected edits, and the baseline mode. Historical attribution is available only for recorded receipts; older sessions without receipts display `unknown` rather than inferred revision usage. Evaluation uses matched long coding and research tasks with equal provider, task limits, and outcome checks. Compare task completion and cost per successful task against existing compaction. Log cache changes; do not report token savings as task-quality or dollar gains without those measurements. Live paid evaluation requires separate authorization and a budget. Disabled-mode behavior, daemon startup, and manual inspection of the accepted context are verification gates before release.
